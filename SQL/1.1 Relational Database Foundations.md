# What is a Database?

A **database** is an organized collection of data designed so that the data can be **stored, accessed, managed, and updated efficiently**.

## Example

A college may have a database containing:

```text
Students
Courses
Faculty
Departments
Attendance
Marks
Fees

Placements
```

Think of a database as a **digital organized storage system**.
A database is the **data + structure**.

# Why Do We Need Databases?

Imagine storing **100,000 student records** in: 
```text 
students.txt
```

You want to:

> Find all CSE students with CGPA > 8.5.

Without a database system, you might have to **manually scan the file**.

A database system can execute:

```code
SELECT *
FROM students
WHERE department = 'CSE'
  AND cgpa > 8.5;
```

## Problems with ordinary file storage

Traditional file systems have problems with:

## 1 ) Data redundancy

``` text
Same data appears multiple times.

Student ID 101
Pradeep
CSE

Student ID 101
Pradeep
CSE
```

## 2 ) Data inconsistency

``` text
One file says:

Department = CSE

Another says:

Department = IT

Which one is correct?
```

## 3 ) Difficult searching

```text
Finding specific records becomes difficult as data grows.
```
## 4 ) Concurrent access

```text
What happens if:

User A → updates account
User B → reads account
User C → updates account
at exactly the same time?
```

## 5 ) Security

```text
Different users may require different levels of access.

Example
Admin   → Everything
Teacher → Marks
Student → Own marks

Traditional file systems can make fine-grained access control difficult.

Database systems provide mechanisms such as:

- Authentication
- Authorization
- Roles
- Permissions
- Access control
```

## 6) Recovery

```text
What happens when something goes wrong?

Possible failures include:

- Server crash
- Power failure
- Disk failure
- Application failure
  
Without proper recovery mechanisms, data may be lost or corrupted.
Database systems provide **backup and recovery mechanisms** to restore data after failures.

```

## 7) Integrity

```text

Data integrity ensures that stored data remains accurate, valid, and consistent.

For example, suppose the valid departments are:
1. CSE
2. ECE
3. EEE
4. MECH
5. CIVIL

We don't want invalid data such as:

Student Department = XYZXYZ

Database systems use constraints and validation rules to prevent invalid data from being stored.

```

# How Database Systems Solve These Problems

|Problem|Database Solution|
|---|---|
|Data Redundancy|Data organization and normalization|
|Data Inconsistency|Constraints and centralized data management|
|Difficult Searching|SQL queries and indexes|
|Concurrent Access|Transaction and concurrency control|
|Security|Authentication, roles, and permissions|
|Recovery|Backup and recovery mechanisms|
|Integrity|Constraints and validation rules|

> [!IMPORTANT]  
> Database systems are designed to solve the problems that arise when storing, managing, accessing, and updating large amounts of data using ordinary files.

# What is the Relational Model?

The relational model represents data as **relations**.

In practical SQL:

> A relation is commonly represented as a table.

For example:


# Natural Key vs Surrogate Key

Natural Key :
A real-world attribute used as an identifier.
```text
email
aadhaar_number
passport_number
```

Surrogate Key:
An artificial identifier created specifically for the database.
```text

```

```
Why use surrogate keys?

Because real-world identifiers can:

- change
- be long
- have business meaning
- have complicated uniqueness rules
```

# Foreign Key

A **foreign key** establishes a relationship between tables and helps maintain referential integrity.

```text

T1 - departments

department_id | name
--------------+-----
1             | CSE
2             | ECE

AND

T2 - students

student_id | name    | department_id
-----------+---------+--------------
101        | Pradeep | 1
102        | Arun    | 2

Here
students.department_id
references:
departments.department_id


FOREIGN KEY (department_id)
REFERENCES departments(department_id)

```

## Why Foreign Keys Exist?

Foreign keys prevent this when the constraint is enforced.

This is called:

> **Referential integrity**

>[!info]
>PostgreSQL describes foreign keys as constraints requiring referencing values to identify matching rows in another table, thereby maintaining referential integrity.

# Primary Key vs Foreign Key

| Primary Key                 | Foreign Key              |
| --------------------------- | ------------------------ |
| Identifies rows             | References rows          |
| Must be unique              | Need not be unique       |
| Cannot be NULL              | Can often be NULL        |
| One PK constraint per table | Multiple FKs possible    |
| Defines entity identity     | Defines relationship     |
| Parent table often has it   | Child table often has it |
## Can Foreign Key Contain Duplicates?
Yes.
```text
students

student_id | department_id
-----------+--------------
101        | 1
102        | 1
103        | 1
104        | 2

Multiple students can belong to the same department.
Foreign key ≠ unique
```
## Can Foreign Key Be NULL?

Yes, Generally
```text
employee_id | manager_id
------------+-----------
101         | NULL
102         | 101
103         | 101

Maybe employee 101 has no manager.

manager_id INT NOT NULL
REFERENCES employees(employee_id)
```

>[!info]
>PostgreSQL notes that a referencing row normally does not have to satisfy the foreign-key match if one of its referencing columns is NULL; `NOT NULL` can be used when that should not be allowed.
